## Summary (읽기 전에 30초)

| 항목 | 내용 |
|---|---|
| **증상** | "소파 추천해줘" 같은 일반 추천 질문 한 번에 상품별 상세조회(`get_product_detail`)가 반복 호출되며 당시 라운드 상한(4)을 다 써서 응답까지 30~60초 |
| **원인** | `search_products` 응답에 이미 이름·브랜드·가격·카테고리가 담겨 있는데도, "그것만으로 답하라"는 지침이 프롬프트에 없어 후보 상품마다 상세조회를 추가 호출 |
| **해결** | 프롬프트에 절약 지침 추가(정상 흐름 2라운드로 종료) + 라운드 상한 4→3(하드 안전망) |
| **한계** | 라운드 수 감소는 코드로 확인했지만, 수정 후 실제 응답 시간 재측정·이 로직을 고정하는 회귀 테스트·폴백 발생 빈도 집계는 모두 아직 없음 |

## 증상 — 일반 추천 질문이 라운드 상한을 꽉 채움

`GeminiClient.generate()`는 Gemini의 `functionCall` 루프를 최대 `MAX_TOOL_CALL_ROUNDS`번 돈다. 한 라운드는 Gemini API 호출 1회이고, 도구 실행 자체는 로컬 DB 조회라 수 ms에 불과해 대부분의 지연이 이 API 라운드 수에서 나온다. 모델이 텍스트를 반환하면 즉시 종료되고, 아니면 도구를 실행해 다음 라운드로 넘어간다.

"소파 추천해줘"처럼 후보 상품 여러 개를 놓고 답해야 하는 질문에서, 모델이 검색(`search_products`) 이후 후보 상품마다 `get_product_detail`을 추가로 호출하며 당시 상한(4)을 다 채웠고, 상한에 걸리면 규칙 기반 응답으로 폴백하면서 체감 응답 시간이 30~60초까지 늘어졌다(`1fe06e5`).

## 진단 — 이미 있는 정보를 다시 조회하고 있었다

`search_products`가 반환하는 결과에는 이미 이름·브랜드·가격·카테고리가 담겨 있어 일반적인 추천 답변에는 그것만으로 충분하다. 그런데 프롬프트에 "그 정보만으로 답하라"는 지침이 없다 보니, 모델이 후보 상품마다 더 자세한 정보를 얻으려고 `get_product_detail`을 반복 호출했다.

```
R1  search_products
R2  get_product_detail (후보 1)
R3  get_product_detail (후보 2)
R4  상한 도달 → 규칙 기반 응답으로 폴백
```

## 해결 — 프롬프트 지침 + 라운드 상한을 함께 낮춤

```java
// ChatService.java — 시스템 프롬프트에 추가
"응답 속도를 위해 도구 호출은 최소한으로 하세요. search_products 결과에는
이미 이름/브랜드/가격/카테고리가 담겨 있으니, 추천 답변은 그 정보만으로
작성하세요. 고객이 특정 상품 하나를 콕 집어 '더 자세히'를 요청한 경우가
아니면 get_product_detail을 부르지 마세요."
```

```java
// GeminiClient.java
private static final int MAX_TOOL_CALL_ROUNDS = 3; // was 4
```

프롬프트 지침만으로는 모델이 매번 따른다는 보장이 없는 soft guidance이기 때문에, 코드 레벨의 하드 상한도 함께 낮춰 안전망으로 남겼다. 정상 흐름은 검색 1라운드 + 답변 1라운드(총 2라운드)로 끝나고, 상한을 넘기면 기존 원칙대로 예외 대신 규칙 기반 응답으로 조용히 폴백한다.

```
R1  search_products
R2  텍스트 답변 종료
```

## 트레이드오프 — 라운드 상한을 어디까지 낮출 것인가

라운드 상한을 2까지 낮추면 지연 상한을 더 확실히 보장할 수 있었지만, "이 소파 소재가 뭐예요?"처럼 상품 하나를 콕 집어 상세조회가 실제로 필요한 정상 케이스(검색+상세조회+답변=3라운드)까지 한도 초과로 폴백돼버린다는 걸 확인했다. "항상 빠르지만 가끔 대답을 못 한다"보다 "대부분 빠르고 드문 케이스만 한 라운드 더 쓴다"를 택해 3을 남겼다.

같은 이유로 `get_product_detail` 자체를 코드로 비활성화하는 안도 검토했지만, 그러면 정말 상세조회가 필요한 질문까지 못 받게 되어 기각했다. 도구를 막는 대신 프롬프트로 모델이 스스로 아끼도록 유도하는 쪽을 택했다.

## 참고 — 같은 세션에서 발견된 별개 문제

지연 문제를 고치던 중, 원인이 전혀 다른 버그를 하나 더 발견했다(`a17172c`). `tools`를 포함한 큰 요청에서 Gemini가 유효한 JSON을 반환하면서도 `Content-Type`을 `application/octet-stream`으로 잘못 내려보내는 경우가 있었는데, 이게 무료 할당량 소진(429)에 가려져 있다가 유료 티어 전환 후 실제 200 응답을 받으면서 드러났다. `.body(Map.class)` 대신 `.body(String.class)`로 받아 `ObjectMapper`로 직접 파싱하도록 바꿔, `Content-Type` 기반 컨버터 선택에 더 이상 의존하지 않게 했다. 지연 문제와는 원인이 다르지만 같은 `GeminiClient` 안정화 세션, 같은 파일에서 함께 고쳐진 문제라 같이 남겨둔다.

## Metrics

| 지표 | 수정 전 | 수정 후 (`1fe06e5`) |
|---|---|---|
| `MAX_TOOL_CALL_ROUNDS`(하드 상한) | 4 | 3 (-25%) |
| 일반 추천 질문의 정상 흐름 라운드 수 | 최대 4 | 2 (-50%) |
| "소파 추천해줘" 관측 응답 시간 | 30~60초 | 재측정 기록 없음 |
| 추천 후보 N개당 상세조회 호출 | 최대 N회 | 0회(콕 집어 물을 때만 1회) |
| 이 라운드 예산을 고정하는 테스트 | 0 | 0 |

라운드 수는 `GeminiClient.generate()`의 `for` 루프 상한과 종료 조건을 코드로 직접 확인한 값이고, 응답 시간은 재측정 기록이 없어 수정 전 관측치만 남아 있다(2026-08-31 기준 저장소 전수 확인 결과).

## 재발 방지 · 남은 과제

- 코드에 `MAX_TOOL_CALL_ROUNDS`를 왜 3으로 뒀는지, 2로 낮추면 어떤 케이스가 깨지는지 설명하는 주석을 직접 남겨, 다음에 이 값을 만질 사람이 같은 조사를 반복하지 않도록 했다.
- **재측정이 안 됨**: "30~60초"는 수정 전 증상 기록일 뿐, 수정 후 몇 초로 줄었는지는 실측하지 않았다. 라운드 수 감소와 체감 지연 감소는 서로 다른 주장이라, `GeminiClient.generate()`에 라운드 수·총 소요시간 로그를 남기는 게 가장 싼 확인 수단인데 아직 없다.
- **회귀 테스트가 없음**: 프롬프트 지침은 모델이 매번 따른다는 보장이 없는 soft guidance지만, 코드가 실제로 보장하는 "최대 3라운드에서 멈춘다"는 사실조차 테스트로 고정돼 있지 않다(Chat/Gemini 관련 테스트 0개). Gemini API를 목(mock)으로 대체하면 비용 없이 라운드 루프 로직만 고정할 수 있다.
- **폴백 빈도를 모름**: 라운드 상한에 걸려 규칙 기반 응답으로 내려간 경우가 실제로 얼마나 자주 발생하는지 집계하는 수단이 없다. 지금은 `log.warn`에만 남고 집계되지 않아, "3이 충분한 여유인지"를 사후에 확인할 방법이 없다.
