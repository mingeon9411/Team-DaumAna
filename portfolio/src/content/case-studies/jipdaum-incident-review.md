## 1. PASS 인증 전환이 촉발한 로그인 전면 차단 + 배포 정지 복합 장애

**기간**: 2026-08-23 (`1b14****` → `94ea****` → `79f1****`)
**심각도**: 최상 — 신규 가입/로그인이 프로덕션에서 전부 실패, 원인 파악 도중 배포 자체가 멈춰 수정 커밋이 반영조차 안 되는 이중 장애.

### 증상
hCaptcha 위젯을 실제 통신사 PASS 인증 흐름처럼 보이게 하는 데모 컴포넌트로 교체한 뒤, 운영 도메인(`<PROD_DOMAIN>`)에서 회원가입·로그인·소셜로그인이 전부 실패했다.

### 진단
1. 새 데모 컴포넌트는 검증 없이 더미 토큰만 만들어 백엔드로 보내는 화면 흐름 재현용이었다.
2. 반대로 백엔드는 그 값을 진짜 hCaptcha 검증 API로 검사했다 — 당연히 hCaptcha 서버가 mock 토큰을 전부 거부.
3. 프론트만 되돌리면 끝날 문제였는데, 되돌린 커밋을 배포해도 운영 화면에 `hCaptcha has failed to initialize` 에러가 계속 남았다.
4. 사이트 키 환경변수가 애초에 전환 커밋에서 예제 파일과 함께 지워지며 배포 플랫폼 환경변수에서도 빠져 있던 것을 확인, 재등록.
5. 그런데도 동일 에러 지속 — 프론트 빌드 환경변수는 **빌드 시점에 번들에 굳어지므로** 변수만 등록해도 재빌드 전까지는 반영되지 않는다는 걸 재확인.
6. CI 상태 API로 커밋별 배포 빌드 상태를 직접 조회하니, `main`이 새 커밋을 여러 개 쌓았는데도 배포 플랫폼이 예전 커밋에 멈춰 새 빌드를 시도조차 안 하고 있었다.
7. 같은 시점에 빌드 도구 메이저 버전이 올라가 있었는데, 그 도구가 요구하는 Node 버전을 배포 플랫폼 기본 Node 버전이 못 맞춰 빌드가 조용히 실패(또는 스킵)하고 있었다.

### 근본 원인
애플리케이션 레벨(프론트 mock 토큰 ↔ 백엔드 실검증, 서로 다른 신뢰 모델로 배포되어 계약 파손)과 인프라 레벨(빌드 도구 요구 Node 버전 ↔ 배포 플랫폼 기본 Node 버전 불일치)이 같은 시점에 겹친 복합 장애.

### 해결
- 데모 컴포넌트 제거, 관련 화면들을 원래의 캡차 위젯으로 복원. 별도 저장소의 백엔드 검증 호출 지점도 함께 원복.
- 사이트 키를 예제 파일 + 배포 플랫폼 환경변수에 재등록.
- Node 버전 고정 파일 추가 + `package.json`에 엔진 범위를 명시해 배포 플랫폼이 올바른 Node 버전으로 빌드하도록 강제.

### 재발 방지
- 프론트/백엔드가 토큰 포맷을 공유하는 기능은 두 저장소를 **같은 커밋 타이밍에** 되돌릴 수 있어야 한다 — 한쪽만 롤백하면 계약이 다시 깨진다.
- 빌드 도구 메이저 업그레이드는 배포 플랫폼 런타임 버전 고정과 항상 세트로 커밋한다.
- "코드를 고쳤는데도 운영에 안 보인다"는 신호가 오면 코드 문제로만 보지 말고 배포 파이프라인이 새 커밋을 실제로 물어가고 있는지부터 확인한다.

## 2. 상품 이미지 원본 용량 폭증(107MB) → 배포된 메인 페이지가 완전히 빈 화면

**기간**: 2026-08-24 (`2b6d****`)
**심각도**: 높음

### 증상
메인 상품 14종을 새 사진으로 전면 교체해 배포하자, 로컬에서는 멀쩡했던 화면이 운영 배포본에서는 아무것도 뜨지 않았다.

### 진단 · 근본 원인
새로 받은 상품 사진 14장이 원본 그대로(장당 5~13MB, 합계 107MB) 커밋돼 있었다. 로컬 개발 서버(파일시스템 직접 서빙)는 체감 지연이 적었지만, 실제 네트워크를 거치는 배포 환경에서는 초기 페인트에 필요한 리소스를 사실상 못 받아와 빈 화면으로 보였다 — 이미지 최적화 단계 없이 디자인 원본을 그대로 정적 자산 파이프라인에 커밋한 것이 원인. 로컬 QA만으로는 드러나지 않는 유형이었다.

### 해결
리사이즈(표시 크기 이내) + 재인코딩으로 합계 107MB → 1.5MB로 축소. 이후 추가되는 이미지도 같은 파이프라인을 거쳐 커밋하도록 절차화(`df4e****`).

### 재발 방지
- 상품/에셋 이미지는 커밋 전 리사이즈+재인코딩을 기본 절차로 굳힘.
- 배포 확인은 CI/배포 플랫폼 API로 실제 빌드·서빙 상태를 직접 조회하는 흐름으로 전환.

## 3. API 응답이 배열이 아닐 수 있다는 걸 검증 안 해 홈페이지 전체가 크래시

**기간**: 2026-08-25 (`7823****`)
**심각도**: 높음 — 특정 기능 하나가 아니라 홈페이지 전체가 렌더링 도중 죽는 React 크래시.

### 증상
다른 성능 개선 작업 중, 실제로는 홈페이지 자체가 `X.map is not a function`으로 완전히 크래시하고 있는 것을 발견했다.

### 진단 · 근본 원인
목록 조회 API 응답을 검증 없이 그대로 state에 넣고 렌더링에서 바로 `.map()`을 호출하고 있었다. 백엔드가 예상과 다른 응답(비로그인 안내, 에러 객체 등 배열이 아닌 값)을 준 순간 컴포넌트 트리 전체가 터졌다. 이전에도 같은 계열 버그(`b0ac****`)를 고친 적이 있어 같은 패턴이 또 있는지 전수 점검했더니, 총 **5곳**에서 발견됐다 — 한 번의 부주의가 아니라 반복된 설계 습관이었다.

### 해결
5곳 모두에 배열 여부를 확인하는 타입 가드를 추가해, 백엔드가 예상과 다른 응답을 줘도 해당 화면만 빈 상태로 넘어가고 페이지 전체가 죽지 않도록 격리했다.

### 재발 방지
- API 응답을 state에 넣기 전 타입 가드를 통과시키는 걸 팀 컨벤션으로 굳힘(이후 커밋 `7ace****`도 동일 패턴 준수).
- 크래시 재현을 계기로 "다른 곳에도 같은 버그가 더 있는가"를 항상 같이 확인하는 습관 — 최초 증상과 실제 버그가 다를 수 있다.

## 4. 백엔드 커스텀 유저 모델 참조 오류로 셸·마이그레이션이 완전히 막힘

**기간**: 초기 백엔드 구축 단계 (`4464****` 이전 로컬 작업)
**심각도**: 중간 — 배포 영향은 없었지만 로컬 개발이 완전히 멈추는 블로커.

### 증상 · 진단
커스텀 유저 모델을 지정하는 설정값이 예전 앱 이름을 그대로 가리키고 있었는데, 실제 유저 모델은 이미 리팩터링을 거쳐 별도 앱으로 분리된 상태였다. 프레임워크는 이 설정값을 `앱이름.모델명` 문자열로 앱 레지스트리에서 그대로 찾기 때문에, 앱 분리 시점에 같이 안 바꾸면 임포트가 아니라 런타임 조회 단계에서 실패한다.

### 근본 원인
모델을 다른 앱으로 옮기는 리팩터링을 하면서, 문자열로 참조되어 있어 IDE의 "참조 찾기"에 걸리지 않는 설정값을 같이 갱신하지 않은 것.

### 해결 · 재발 방지
설정값을 새 앱 경로로 수정. 이후 문자열로 참조되는 설정(커스텀 유저 모델, 문자열 기반 외래키 등)은 모델을 다른 앱으로 옮길 때 같이 검색해서 갱신하는 걸 체크리스트에 넣음 — 정적 분석/IDE 리팩터링 도구가 못 잡는 지점이라서.

## 5. 파일명 대소문자 불일치 — 로컬(Windows)은 정상, CI(Linux)만 빌드 실패

**기간**: 2026-08-20 (`694f****`)
**심각도**: 중간 — 기능 자체엔 문제가 없었지만 배포 파이프라인이 계속 실패해 머지된 코드가 운영에 반영되지 않는 상태.

### 증상 · 진단
CI(Linux 러너)에서 프론트 빌드가 모듈을 찾지 못하는 에러로 계속 실패했지만, 로컬(Windows)에서는 동일 코드가 문제없이 빌드됐다. 실제 파일명과 import 경로의 대소문자가 서로 달랐던 것 — Windows/Mac의 기본 파일시스템은 대소문자를 구분하지 않아 로컬에서는 그냥 매칭돼 열렸지만, CI 러너(Linux)는 대소문자를 엄격히 구분해 그 경로가 존재하지 않는 것으로 처리했다.

### 근본 원인
개발 환경의 대소문자 비구분 파일시스템이 애초에 있던 파일명/import 경로 불일치를 가려주고 있었을 뿐인 잠재 버그.

### 해결 · 재발 방지
실제 파일명을 import 경로와 동일하게 통일. 이런 유형의 버그는 로컬에서 아무리 테스트해도 재현되지 않는다는 걸 팀 규칙으로 인지 — CI가 Linux 러너를 쓰는 이상 "로컬에서 됐다"는 검증이 되지 않는다.

## 6. 브라우저 창 리사이즈 시 가로 스크롤 패널이 서로 겹쳐 보이는 문제

**기간**: 2026-08-30
**심각도**: 낮음~중간 — 메인 페이지 핵심 연출(가로 스크롤 패널)이 창 크기를 바꿀 때마다 깨져 보이는 시각적 버그.

### 증상 · 진단
브라우저 창을 최소화했다가 최대화(또는 임의로 리사이즈)하면 특정 패널이 화면에 딱 맞게 나오지 않고 옆 패널과 겹쳐 보였다. 스크롤 라이브러리 소스를 직접 열어 확인해보니, resize 이벤트가 오면 뷰포트 치수만 갱신할 뿐 현재 보던 패널로 다시 스냅해주는 로직이 없었다. 각 패널의 문서 기준 좌표는 리사이즈 관찰자가 잡히는 시점에 **500ms 디바운스**로만 갱신된다는 것도 확인했다. 처음에 "리사이즈 후 200ms 뒤 재스냅" 핸들러를 추가했더니 증상이 그대로 재현됐다 — 라이브러리 내부 500ms 디바운스보다 먼저 실행되어 아직 갱신 안 된 좌표 기준으로 스냅했기 때문.

### 근본 원인
패널 폭이 뷰포트 단위 기반이라 창 크기가 바뀌면 패널 폭 자체가 바뀌는데, 스크롤 라이브러리가 기억하는 스크롤 위치(px)는 리사이즈 전 값 그대로 남아 두 패널이 반씩 걸쳐 보이는 것.

### 해결
resize 리스너를 추가해, 리사이즈가 끝나면(디바운스) 스크롤 한계를 다시 계산하고 현재 패널로 재정렬한다. 디바운스 지연은 라이브러리 내부 좌표 갱신(500ms)보다 반드시 늦게 실행되도록 600ms로 설정했다.

### 재발 방지
- 서드파티 라이브러리가 "리사이즈에 대응한다"고 해서 "현재 상태를 일관되게 유지한다"는 뜻은 아니다 — 치수만 갱신하고 위치 보정은 안 해주는 경우가 있으니, 라이브러리 소스를 직접 열어 어디까지 자동 처리하는지 확인한 뒤 나머지를 채워 넣어야 한다.
- 여러 디바운스/타이머가 같은 이벤트에 반응할 때는 실행 순서를 명시적으로 보장해야 한다.
