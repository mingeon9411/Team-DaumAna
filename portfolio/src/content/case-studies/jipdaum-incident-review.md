## 1. PASS 인증 전환이 촉발한 로그인 전면 차단 + 배포 정지 복합 장애

**기간**: 2026-08-23 (`1b14****` → `94ea****` → `79f1****`)
**심각도**: 최상 — 신규 가입/로그인이 프로덕션에서 전부 실패, 원인 파악 도중 배포 자체가 멈춰 수정 커밋이 반영조차 안 되는 이중 장애.

### 증상
hCaptcha 위젯을 실제 통신사 PASS 인증 흐름처럼 보이게 하는 데모 컴포넌트로 교체한 뒤, 운영 도메인(`<PROD_DOMAIN>`)에서 회원가입·로그인·소셜로그인이 전부 실패했다.

### 진단
1. 새 데모 컴포넌트는 검증 없이 더미 토큰만 만들어 백엔드로 보내는 화면 흐름 재현용이었다.
2. 반대로 백엔드는 그 값을 진짜 hCaptcha 검증 API로 검사했다 — 당연히 hCaptcha 서버가 mock 토큰을 전부 거부.
3. 프론트만 되돌리면 끝날 문제였는데, 되돌린 커밋을 배포해도 운영 화면에 `hCaptcha has failed to initialize` 에러가 계속 남았다.
4. 사이트 키 환경변수가 애초에 전환 커밋에서 예제 파일과 함께 지워지며 배포 플랫폼 환경변수에서도 빠져 있던 것을 확인, 재등록.
5. 그런데도 동일 에러 지속 — 프론트 빌드 환경변수는 **빌드 시점에 번들에 굳어지므로** 변수만 등록해도 재빌드 전까지는 반영되지 않는다는 걸 재확인.
6. CI 상태 API로 커밋별 배포 빌드 상태를 직접 조회하니, `main`이 새 커밋을 여러 개 쌓았는데도 배포 플랫폼이 예전 커밋에 멈춰 새 빌드를 시도조차 안 하고 있었다.
7. 같은 시점에 빌드 도구 메이저 버전이 올라가 있었는데, 그 도구가 요구하는 Node 버전을 배포 플랫폼 기본 Node 버전이 못 맞춰 빌드가 조용히 실패(또는 스킵)하고 있었다.

### 근본 원인
애플리케이션 레벨(프론트 mock 토큰 ↔ 백엔드 실검증, 서로 다른 신뢰 모델로 배포되어 계약 파손)과 인프라 레벨(빌드 도구 요구 Node 버전 ↔ 배포 플랫폼 기본 Node 버전 불일치)이 같은 시점에 겹친 복합 장애.

### 해결
- 데모 컴포넌트 제거, 관련 화면들을 원래의 캡차 위젯으로 복원. 별도 저장소의 백엔드 검증 호출 지점도 함께 원복.
- 사이트 키를 예제 파일 + 배포 플랫폼 환경변수에 재등록.
- Node 버전 고정 파일 추가 + `package.json`에 엔진 범위를 명시해 배포 플랫폼이 올바른 Node 버전으로 빌드하도록 강제.

### 재발 방지
- 프론트/백엔드가 토큰 포맷을 공유하는 기능은 두 저장소를 **같은 커밋 타이밍에** 되돌릴 수 있어야 한다 — 한쪽만 롤백하면 계약이 다시 깨진다.
- 빌드 도구 메이저 업그레이드는 배포 플랫폼 런타임 버전 고정과 항상 세트로 커밋한다.
- "코드를 고쳤는데도 운영에 안 보인다"는 신호가 오면 코드 문제로만 보지 말고 배포 파이프라인이 새 커밋을 실제로 물어가고 있는지부터 확인한다.

## 2. 설정 키 하나가 프로덕션 API 전체를 502로 멈춘 사고

**기간**: 2026-08-28 (`26ba****` → `e243****`)
**심각도**: 최상 — 배포 파이프라인은 success로 종료됐지만 실제로는 프로덕션 전체 API가 502로 응답 불가 상태.
**임팩트**: GitHub Actions 배포 완료 시각 기준 장애 지속 **3시간 9분**(원인 배포 완료 01:21 UTC → 수정 배포 완료 04:30 UTC), 실제 수정은 파일 1개·5줄.

```text
[CORS 설정 키 추가 커밋] → GitHub Actions 빌드 success
        └─ 컨테이너 기동 시 기본값 없는 @Value 바인딩 실패
              └─ Spring 컨텍스트 초기화 실패, 컨테이너는 즉시 종료
                    └─ 배포 스크립트는 기동 여부를 확인하지 않음 → 파이프라인 success 유지
                          └─ 운영 도메인 전체 API 502 (3시간 9분 지속)
```

### 증상
CORS 허용 origin을 로컬 개발 도메인과 운영 도메인 두 곳에 동시에 허용하려고 신규 설정 키(`app.cors-allowed-origins`)를 추가해 배포했다. GitHub Actions 배포 로그는 `success`로 끝났는데, 배포 직후 운영 도메인에서 로그인·상품 조회 등 모든 API가 502를 반환했다.

### 진단
1. 처음엔 CORS 설정 자체가 잘못됐다고 의심했다 — 그런데 502는 CORS 정책 위반(403 preflight 거부)이 아니라 서버가 아예 응답하지 못하고 있다는 신호였다. 의심을 "설정값 문제"에서 "서버 기동 실패"로 옮겼다.
2. 시크릿이 포함된 `application.yml`은 저장소에 커밋하지 않는 구조라, 로컬과 운영 서버가 서로 다른 설정 파일을 갖는다는 걸 다시 짚었다.
3. 코드를 보니 신규 설정 키가 기본값 없는 `@Value`였다 — 서버 쪽 설정 파일엔 이 키가 아직 없으므로 Spring 컨텍스트 초기화 자체가 실패하는 구조였다.
4. 배포 스크립트가 컨테이너 기동 성공 여부를 확인하지 않는 fire-and-forget 방식이라는 것도 확인했다 — 컨테이너가 뜨자마자 죽어도 파이프라인은 success로 끝난다.

### 근본 원인
시크릿 관리를 위해 설정 파일을 저장소에서 제외한 구조가, 배포 시 신규 설정 키를 서버에 동기화하는 절차 없이 운영되고 있었다. 여기에 배포 스크립트가 컨테이너 기동 여부를 검증하지 않는 fire-and-forget 방식이 겹쳐, "배포 성공"과 "서비스 정상"이 별개로 취급되고 있었다.

### 해결
새 설정 키가 없어도 기존 값(`app.frontend-url`)으로 자동 폴백하도록 중첩 플레이스홀더를 적용했다.

```java
// 서버 application.yml엔 새 키가 아직 없을 수 있다 — 없으면 기존 키로
// 폴백해 컨텍스트 초기화 실패(=배포 시 전체 다운)를 막는다.
@Value("#{'${app.cors-allowed-origins:${app.frontend-url}}'.split(',')}")
private List<String> corsAllowedOrigins;
```

별도 검증 로직 대신 프로퍼티 표현식만으로 끝낸 이유는, 문제의 본질이 "값이 틀림"이 아니라 "값이 아예 없을 수 있음"이었기 때문이다. 배포 전 해당 프로퍼티를 일부러 뺀 설정으로 실제 기동 테스트를 거쳐 폴백 동작을 확인한 뒤 재배포했다.

### 재발 방지
- 새 설정 키를 추가할 때는 기본값 또는 기존 키로의 폴백을 함께 넣는 걸 코드 리뷰 체크리스트에 명문화.
- 배포 후 컨테이너 기동 여부를 확인하는 헬스체크 스텝 추가를 다음 개선 과제로 등록(현재는 미반영).
- 이 사고를 계기로 직전에 겪은 별개의 설정 관련 이슈(메일 발송 실패, 인증 실패 로그 부재)까지 함께 다시 살펴, "신규 설정 키·시크릿이 서버에 반영됐는지 배포 파이프라인이 검증하지 않는다"는 공통 원인으로 수렴시켜 기록.

## 3. 인증 크래시 버그가 20일 뒤 다른 경로로 재발

**기간**: 2026-08-07 (`2b2d****`) → 2026-08-27 (`90b0****`)
**심각도**: 높음 — 검증 실패가 걸리는 모든 엔드포인트(회원가입·로그인·장바구니·주문·결제 등 19개)가 노출.
**임팩트**: 1차 수정 배포 완료(2026-08-07 04:21 UTC)부터 재발 수정 배포 완료(2026-08-27 06:17 UTC)까지 정확히 **20일 1시간 56분**, 1차 수정이 커버한 범위는 19개 중 0개.

```text
[미인증 요청]                          [@Valid 검증 실패]
      │                                       │
      ▼                                       ▼
Spring Security 필터                   컨트롤러 예외 미처리
anyRequest().authenticated()           → 기본 /error로 포워딩
      │                                       │
      └───────────────┬───────────────────────┘
                       ▼
            둘 다 같은 302 리다이렉트
                       ▼
        프론트가 HTML을 JSON으로 파싱 시도 → 크래시

1차 수정(2b2d579)은 왼쪽 경로만 차단 → 20일 뒤 오른쪽 경로로 재발
```

### 증상
로그인 토큰이 만료된 채 접근하면, 프론트엔드가 정상적인 401 JSON 대신 로그인 페이지 HTML을 200으로 받아 크래시했다. 1차로 인증 진입점(Entry Point)의 스코프를 좁혀 수정해 미인증 요청 경로는 해결했다(`2b2d****`). 20일 뒤, 이번엔 회원가입 시 입력값 검증(`@Valid`) 실패 케이스에서 똑같은 증상이 재발했다.

### 진단
1. 처음엔 지난번 수정이 롤백됐는지 의심했지만, Git 이력상 1차 수정은 그대로 살아있었다 — 같은 증상, 다른 원인이라는 뜻이었다.
2. 코드를 추적해보니 Spring Security의 미인증 처리 경로와, 처리되지 않은 서버 예외가 포워딩되는 경로는 서로 다른 코드지만 둘 다 같은 인증 필터 규칙(`anyRequest().authenticated()`)에 걸려 같은 302 리다이렉트로 귀결됐다.
3. 1차 수정은 "미인증 요청"이라는 진입점 하나만 막았을 뿐, "처리되지 않은 예외"라는 더 넓은 카테고리는 건드리지 않아 재발한 것으로 확인.
4. `@Valid`를 쓰는 컨트롤러 메서드를 전수 검색해 영향 범위를 확정 — 19개 엔드포인트가 같은 위험에 노출돼 있었다.

### 근본 원인
증상(302 → HTML 응답)이 동일해 하나의 원인으로 오인하기 쉬웠지만, 실제로는 서로 다른 두 코드 경로가 같은 필터 규칙에 걸려 같은 증상을 내는 구조였다. 1차 수정이 진입점 하나만 막는 국소적 패치였던 것이 재발의 직접 원인.

### 해결
엔드포인트마다 예외를 잡는 대신, 전역 예외 핸들러(`GlobalExceptionHandler`) 한 곳에 `MethodArgumentNotValidException`과 그 외 모든 미처리 예외를 잡는 핸들러를 추가해, 예외가 프론트까지 도달하는 통로 자체를 하나로 통일했다.

```java
// @Valid 실패는 여기 없으면 Boot 기본 /error로 빠져 302 문제를 겪는다.
// 프론트가 기대하는 {"필드": message} 모양으로 맞춰야 에러 표시가 동작한다.
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<?> handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
    Map<String, Object> body = new LinkedHashMap<>();
    for (FieldError fe : e.getBindingResult().getFieldErrors())
        body.putIfAbsent(fe.getField(), fe.getDefaultMessage());
    return ResponseEntity.badRequest().body(body);
}
```

프론트가 기대하는 필드별 에러 응답 형식(`{"필드": message}`)에 맞춰 반환하도록 통일했다.

### 재발 방지
- "새 예외를 던지는 코드를 추가하면 전역 핸들러에 걸리는지 확인한다"를 자체 코드 검수 체크리스트에 추가.
- 증상이 같다고 원인도 같다고 단정하지 않는다는 걸 팀 규칙으로 인지 — 재발 시 1차 수정의 적용 범위를 다시 검토하고 더 넓은 카테고리로 일반화.

## 그 외 트러블슈팅 (요약)

이 2건은 위 3건만큼 임팩트가 크진 않았지만, 겪었던 문제와 대응은 아래와 같다. React/Vite 프론트엔드 단독 원인 장애 4건(상품 이미지 용량, API 타입 미검증, 파일명 대소문자, 리사이즈 스냅)은 [프론트엔드 케이스 스터디](/case-studies/jipdaum-frontend-incident-review)로 분리해서 깊게 다뤘다.

- **백엔드 커스텀 유저 모델 참조 오류로 로컬 개발이 완전히 막힘**. 앱 분리 리팩터링 때 문자열로 참조되는 설정값을 같이 안 바꾼 것이 원인 — 참조 경로 수정 + 체크리스트화.
- **동시 주문 시 쿠폰이 사용 한도를 넘겨 소진될 수 있는 TOCTOU 경쟁 조건**. 보안 자체 점검 중 코드 리뷰로 발견, 애플리케이션 락 대신 DB 조건부 `UPDATE`로 원자화(`e7a5****`).
