## 1. 정적 자산 용량 폭증(107MB) → 배포된 메인 페이지가 완전히 빈 화면

**기간**: 2026-08 (`2b6d****`)
**심각도**: 높음 — 기능 버그가 아니라 페이지 자체가 렌더링되지 않는 것처럼 보였다.

### 증상
메인 상품 14종을 새 사진으로 전면 교체해 배포하자, 로컬 개발 서버에서는 멀쩡했던
화면이 실제 배포본에서는 아무것도 뜨지 않는다는 리포트를 받았다.

### 진단
새로 받은 상품 사진 14장이 최적화 없이 원본 그대로(장당 5~13MB) 커밋돼 있었고,
합계 107MB에 달했다. 로컬 개발 서버는 파일시스템에서 바로 서빙하므로 네트워크
지연이 사실상 0에 가까워 체감이 안 됐지만, 실제 네트워크를 거쳐야 하는 배포
환경에서는 브라우저가 초기 페인트에 필요한 리소스를 받아오는 데만 수십 초가
걸려 사실상 "빈 화면"으로 보였다.

### 근본 원인
이미지 리사이즈/재인코딩 같은 최적화 단계 없이 디자인 원본 파일을 그대로 정적
자산 파이프라인에 커밋한 것. 로컬 QA는 네트워크 지연을 감추기 때문에 이런 유형의
버그는 로컬 테스트만으로는 절대 드러나지 않는다.

### 해결
`sharp`로 표시 크기(1600px 이내)에 맞춰 리사이즈 + JPEG 재인코딩(quality 82)
처리해 합계 107MB → 1.5MB로 축소. 이후 추가되는 이미지(인테리어 컷 등)도 같은
파이프라인을 거쳐 커밋하도록 절차화했고, 카드 이미지 영역도 5:6 비율로 통일해
사진마다 원본 크기가 들쭉날쭉해지는 것 자체를 사전에 차단했다(`df4e****`).

### 재발 방지
- 상품/에셋 이미지는 커밋 전 리사이즈+재인코딩을 기본 절차로 굳힘.
- "로컬에서 잘 보인다"는 배포 환경에서의 로딩 성능을 보증하지 않는다는 걸 팀
  규칙으로 명시 — 배포 확인은 실제 네트워크를 거치는 배포 URL에서 직접 확인.

## 2. API 응답이 배열이 아닐 수 있다는 걸 검증 안 해 홈페이지 전체가 크래시

**기간**: 2026-08 (`7823****`)
**심각도**: 높음 — 특정 컴포넌트 하나가 아니라 홈페이지 전체가 렌더링 도중 죽는
React 크래시.

### 증상
다른 성능 개선 작업(hCaptcha 리소스 preconnect) 중 실제 테스트를 하다가,
홈페이지 자체가 `photoReviews.map is not a function`으로 완전히 크래시하고
있는 것을 우연히 발견했다.

### 진단
포토리뷰 목록 API 응답을 검증 없이 그대로 `setPhotoReviews(res.data)`로
state에 넣고, 렌더링에서 바로 `.map()`을 호출하고 있었다.

```js
// Before — res.data가 항상 배열이라고 가정
getPhotoReviews()
  .then((res) => setPhotoReviews(res.data))
  .catch(() => setPhotoReviews([]));
```

백엔드가 예상과 다른 응답(로그인 필요 안내, 에러 객체 등 배열이 아닌 값)을 준
순간 `.map is not a function`이 렌더 도중 던져지고, React가 그 위 경계까지
전부 언마운트해버려 페이지 전체가 하얗게 죽었다. 이전에도 같은 계열 버그
(비로그인 상태 상품 상세 빈 화면, `b0ac****`)를 고친 적이 있어, 같은 패턴이
코드베이스 다른 곳에도 더 있는지 전수 점검했다.

### 근본 원인
"API는 항상 배열을 준다"는 암묵적 가정 위에 state를 설계하고, 그 가정이 깨지는
경로(오프라인, 인증 만료, 백엔드 에러 응답)에 대한 방어가 없었던 것. 같은 패턴이
검색 결과, 쿠폰 목록(장바구니/한국관 결제 양쪽), 배송조회까지 총 **5곳**에서
발견됐다 — 한 번의 부주의가 아니라 반복된 설계 습관이었다는 뜻이다.

### 해결
```js
// After
getPhotoReviews()
  .then((res) => setPhotoReviews(Array.isArray(res.data) ? res.data : []))
  .catch(() => setPhotoReviews([]));
```
5곳 모두에 동일한 타입 가드를 추가해, 백엔드가 예상과 다른 응답을 줘도 해당
화면만 빈 상태로 넘어가고 페이지 전체가 죽지 않도록 격리했다.

### 재발 방지
- API 응답을 state에 넣기 전 타입 가드를 통과시키는 걸 팀 컨벤션으로 굳힘
  (이후 커밋 `7ace****`의 장바구니 카운트 로직도 동일 패턴 준수).
- 크래시 재현을 계기로 "다른 곳에도 같은 버그가 더 있는가"를 항상 같이
  확인하는 습관 — 최초 증상(모달 지연)과 실제 버그(전체 크래시)가 전혀
  다를 수 있다는 걸 재확인한 사례.

## 3. 파일명 대소문자 불일치 — 로컬(Windows)은 정상, CI(Linux)만 빌드 실패

**기간**: 2026-08 (`694f****`)
**심각도**: 중간 — 기능 자체엔 문제가 없었지만, 배포 파이프라인이 계속 실패해
머지된 코드가 운영에 반영되지 않는 상태.

### 증상
GitHub Actions(Linux 러너)에서 프론트 빌드가 `Could not resolve` 에러로 계속
실패했다. 로컬(Windows)에서는 동일 코드가 아무 문제 없이 빌드/실행됐다.

### 진단
실제 파일명과 `import` 경로의 대소문자가 서로 달랐다. Windows(NTFS 기본
설정)와 macOS(APFS 기본 설정)의 파일시스템은 대소문자를 구분하지 않아
로컬에서는 그냥 매칭돼 열렸던 것인 반면, GitHub Actions 러너(Ubuntu, ext4)는
대소문자를 엄격히 구분해 그 경로가 존재하지 않는 것으로 처리했다.

### 근본 원인
개발 환경의 대소문자 비구분 파일시스템이 파일명/import 경로 불일치를
가려주고 있었을 뿐인 잠재 버그.

### 해결
실제 파일명을 import 경로와 동일한 PascalCase로 통일.

### 재발 방지
- 이런 유형의 버그는 로컬에서 아무리 테스트해도 재현되지 않는다 — CI가
  Linux 러너를 쓰는 이상 "로컬에서 됐다"는 검증이 되지 않는다는 걸 인지.
- 이 프로젝트 규모에서는 재발 빈도가 낮아 별도 린트/훅 도입보다, 재발 시
  즉시 대소문자를 통일하는 현재 대응으로 충분하다고 판단(과도한 방지 장치
  대신 비용 대비 효과를 먼저 따짐).

## 4. 브라우저 창 리사이즈 시 가로 스크롤 패널이 서로 겹쳐 보이는 문제

**기간**: 2026-08-30 (`ad4e****`)
**심각도**: 낮음~중간 — 크래시나 배포 실패는 아니지만, 메인 페이지의 핵심
연출(가로 스크롤 패널)이 창 크기를 바꿀 때마다 깨져 보이는 눈에 띄는 버그.

### 증상
브라우저 창을 최소화했다가 다시 최대화(또는 창 크기를 임의로 조절)하면,
특정 패널이 화면 영역에 딱 맞게 나오지 않고 옆 패널의 일부와 겹쳐서 함께
보였다.

### 진단
1. 각 섹션은 `w-screen`(=`100vw`) 폭의 패널을 가로로 나열하고, `lenis` +
   `lenis/snap`(가로 스크롤 + 패널 스냅)으로 화면 전환을 처리한다.
2. `Snap` 라이브러리 소스(`node_modules/lenis/dist/lenis-snap.mjs`)를 직접
   열어 확인해보니, `window resize` 이벤트가 오면 `Snap.onWindowResize`가
   `viewport` 치수만 갱신할 뿐, 현재 보고 있던 패널로 다시 스냅해주는 로직은
   없었다.
3. 각 패널의 "문서 기준 왼쪽 좌표"(`SnapElement.rect.left`)는 스크롤할 때마다
   재계산되는 게 아니라, `document.body`의 `ResizeObserver`가 잡히는 시점에
   **500ms 디바운스**로만 갱신된다는 것도 소스에서 확인했다.
4. 처음에 "리사이즈 후 200ms 뒤 현재 패널로 재스냅"하는 핸들러를 추가했더니
   증상이 그대로 재현됐다 — 라이브러리 내부 500ms 디바운스보다 먼저 실행되어,
   아직 갱신 안 된(리사이즈 전) 좌표 기준으로 스냅해버렸기 때문이었다.

### 근본 원인
패널 폭이 뷰포트 단위(`vw`) 기반이라 창 크기가 바뀌면 패널 폭 자체가 바뀌는데,
스크롤 위치(px)는 리사이즈 전 값 그대로 남는다. 예를 들어 "2번째 패널 시작
= 1920px"였다가 창을 줄이면 실제 2번째 패널 시작은 1280px로 바뀌는데, 스크롤은
여전히 1920px에 멈춰있어 두 패널이 반씩 걸쳐 보이는 것.

### 해결
```js
// App.jsx — Lenis/Snap 초기화 지점
let resizeTimer;
const handleResize = () => {
  clearTimeout(resizeTimer);
  resizeTimer = setTimeout(() => {
    lenis.resize();
    snap.goTo(snap.currentSnapIndex ?? 0); // 현재 패널로 재정렬
  }, 600); // Snap 내부 좌표 갱신(500ms)보다 반드시 늦게
};
window.addEventListener("resize", handleResize);
```
`window resize` 리스너를 추가해, 리사이즈가 끝나면(디바운스) `lenis.resize()`로
스크롤 한계를 다시 계산하고 `snap.goTo()`로 현재 패널로 재정렬한다. 지연 값은
Snap 내부 좌표 갱신(500ms)보다 반드시 늦게 실행되도록 600ms로 설정했다 — 순서를
잘못 잡으면 오히려 증상이 재현된다는 걸 직접 겪었기 때문에 특히 신경 쓴 부분.

### 재발 방지
- 서드파티 라이브러리가 "리사이즈에 대응한다"고 해서 "현재 상태를 일관되게
  유지한다"는 뜻은 아니다 — 치수만 갱신하고 위치 보정은 안 해주는 경우가
  있으니, 라이브러리 소스를 직접 열어 어디까지 자동으로 처리하는지 확인한
  뒤 나머지를 채워 넣어야 한다.
- 여러 개의 디바운스/타이머가 같은 이벤트에 반응해 서로 다른 지연으로 동작할
  때는 실행 순서를 반드시 명시적으로 보장해야 한다.
