## 문제 — 결제 성공 뒤 재고를 차감하면 이미 늦다

기존 흐름은 주문 생성 → PortOne 결제창 → 브라우저의 결제 검증 API → 재고 차감 순서였다. 동시에 같은 옵션을 결제하면 결제는 둘 다 승인됐는데 뒤늦게 재고 차감이 실패할 수 있었고, 이 경우에는 경고 로그만 남긴 채 주문을 완료했다.

쿠폰도 주문 생성 시점에 사용 처리됐고, 장바구니도 즉시 삭제됐다. 결제창을 닫거나 검증 요청이 실패하면 주문은 `PENDING`에 남고 쿠폰만 사라지는 구조였다.

## 선택 — 새 예약 테이블 대신 PENDING 주문을 예약 기록으로 사용

현재 서비스 규모에서는 별도 재고 예약 테이블을 추가하지 않았다. 주문 생성 트랜잭션 안에서 옵션별 조건부 UPDATE를 실행해 재고를 먼저 예약하고, 그 주문의 `PENDING` 상태와 주문 항목을 예약 기록으로 삼았다.

```java
if (option != null &&
    productOptionRepository.decrementStockIfAvailable(option.getId(), qty) == 0) {
    throw new ResponseStatusException(HttpStatus.CONFLICT, "상품 재고가 부족합니다.");
}
```

조건에 맞는 행만 갱신되므로, 동시에 같은 재고를 요구해도 재고보다 많은 주문이 통과하지 않는다. 뒤에서 결제가 성공했을 때는 이미 확보한 재고를 다시 차감하지 않는다.

## 중복 결제 검증 — Payment 행을 잠근 단일 확정 경로

브라우저 재시도나 네트워크 중복 요청이 같은 `merchant_uid`로 동시에 도착할 수 있다. `findByMerchantUidForUpdate`에 비관적 잠금을 적용해 한 요청만 `PENDING → SUCCESS` 전이를 수행하게 했다. 뒤따른 요청은 완료된 결제를 그대로 반환하므로 재고와 배송 번호가 중복 처리되지 않는다.

또한 `payment_id`와 내부 `merchant_uid`가 같은지 확인하고, 현재 로그인 사용자 소유 결제인지 먼저 검사한다. 다른 결제를 조회하거나 식별자를 바꿔 검증 API를 호출하는 경로를 차단했다.

## 쿠폰·주문 취소 복구

결제 준비 전의 PENDING 주문을 취소하면 다음을 같은 트랜잭션에서 복구한다.

| 대상 | 복구 방식 |
|---|---|
| 옵션 재고 | 예약 때 차감한 수량만 다시 증가 |
| 공용 쿠폰 | `used_count`를 음수가 되지 않게 조건부 감소 |
| 개인 쿠폰 | `is_used=false`, `used_at=null`로 되돌림 |

이미 결제가 시작된 주문은 단순 주문 취소를 막았다. 이 상태에서 먼저 재고를 풀어버리면 실제 PG 승인이 늦게 도착했을 때 초과판매가 다시 발생할 수 있기 때문이다.

## 무결제 주문

쿠폰 적용 뒤 결제 금액이 0원이면 PortOne을 호출할 이유가 없다. API 응답에 `payment_required`를 추가하고, Spring은 즉시 `ORDERED`로 전환했다. React 결제 화면과 챗봇 구매 화면은 이 응답을 받으면 결제창 대신 주문 완료 화면으로 이동한다.

## 검증 기록과 범위

| 검사 | 결과 |
|---|---|
| Spring `OrderServiceTest` | 작성 당시 6건 통과 기록 |
| React production build | 작성 당시 빌드 통과 |
| 동시 재고 보호·중복 검증 방지 | DB 조건부 UPDATE와 Payment 비관적 잠금의 코드 구조 확인 |

위 결과는 주문 서비스 테스트와 빌드, 구현 구조를 확인한 범위다. 실제 MySQL에 동시 요청을 보내 재고·결제 상태가 한 번만 변경되는지 검증한 결과와 PG 승인부터 환불까지의 전체 흐름을 검증한 결과는 이 기록에 포함되지 않는다. 실제 이용자 수·주문량도 측정 자료가 없어 상용 트래픽 처리 능력으로 확대해 설명하지 않는다.

## 다음 운영 과제

우선 실제 MySQL에서 마지막 재고에 대한 동시 주문과 동일 결제의 동시 검증을 재현하고, 성공 건수·잔여 재고·주문 및 결제 상태를 함께 검사할 계획이다. 결제창 종료·브라우저 이탈·검증 요청 유실로 남는 예약 상태의 만료·복구도 확인해야 한다.

문서 작성 당시 웹훅과 환불은 별도 구현 과제로 남겨 두었다. 공개 웹훅을 서명 검증 없이 받으면 결제 위변조 통로가 되므로, PortOne V2 웹훅 시크릿의 원문 서명 검증과 PortOne API 재조회가 선행되어야 한다. 이후 결제 실패·만료 정산, 결제 완료 후 환불, 장애 재조회 배치를 같은 상태 전이로 연결하는 것이 후속 범위다.

이 경계를 명시한 이유는 "웹훅 엔드포인트를 추가했다"보다, 실제 금전 상태를 신뢰할 수 있는 방식으로 동기화하는 것이 더 중요하기 때문이다.
