## 배경 · 제약조건

두 프레임워크가 완전히 분리된 DB를 각자 갖는 대신 인스턴스 하나(MySQL)를 공유하기로 한 프로젝트였다. 이 결정 자체는 Django/Spring이 각각 인증·상품/주문 같은 도메인을 나눠 맡는 구조에서 나왔지만, 그 결과 "스키마를 누가 소유하는가"라는 질문이 곧바로 뒤따랐다. 스키마를 두 프레임워크가 동시에 관리하면(Django 마이그레이션 + Hibernate `ddl-auto: update` 등) 서로 다른 시점에 서로 다른 방식으로 테이블을 변경하려다 충돌하는 게 시간 문제였다.

## 의사결정 — 스키마 소유권을 어느 한쪽에 전담시킨다

**선택지**
1. 두 프레임워크가 각자 마이그레이션 도구로 스키마를 관리 (Django migration + Hibernate ddl-auto)
2. 한쪽이 전담 소유하고 다른 쪽은 읽기·쓰기 전용으로 제한

1번은 두 마이그레이션 이력이 어긋나는 순간 스키마가 갈라지는 위험을 안고 간다. 2번을 택했고, 먼저 구축돼 있던 Django 마이그레이션에 소유권을 전담시켰다.

```yaml
# application.yml — Spring은 스키마를 절대 바꾸지 않는다
spring:
  jpa:
    hibernate:
      ddl-auto: none   # Django 마이그레이션이 스키마를 소유
```

이 결정 하나로 "두 시스템이 스키마를 두고 경쟁하는" 클래스의 문제 자체를 원천 차단했다. 다만 예외가 하나 있었다 — 로그아웃 시 토큰 무효화 목록, 소셜 로그인 부가정보처럼 **Spring만 필요로 하고 Django 스키마엔 없는** 테이블이 있었다. 이런 것까지 "스키마는 Django만" 원칙을 문자 그대로 지키면 아예 못 쓰는 기능이 된다.

```java
/**
 * Spring 소유 보조 테이블 users를 없으면 생성한다.
 * Django 스키마가 아니므로 Django 마이그레이션이 만들지 않고, ddl-auto: none이라
 * Hibernate도 만들지 않아 그동안 어느 환경에서도 생성되지 않았다.
 * 여기서 시작 시 한 번 보장해준다 — Spring 소유 테이블만 건드리므로
 * "스키마는 Django가 소유한다"는 원칙과 충돌하지 않는다.
 */
@PostConstruct
public void ensureUsersTable() {
    jdbcTemplate.execute(
        "CREATE TABLE IF NOT EXISTS users (...)"
    );
}
```

원칙을 깨지 않으면서 예외를 수용하는 절충점으로, "Django 테이블은 절대 안 건드리고 Spring 전용 테이블만 만든다"는 조건을 걸어 부팅 시 자가 생성하는 방식을 택했다(`a230****`).

## 실행 — Oracle에서 MySQL로 옮기며 만난 제약조건

스키마 공유 결정과 별개로, 이전까지 쓰던 Oracle에서 MySQL로 엔진 자체를 바꾸는 작업이 같이 필요했다. 세 가지 기술적 차이를 원인부터 추적해서 정리했다.

**드라이버·SQL 함수** — `ojdbc11` → `mysql-connector-j`로 의존성을 교체했고, 네이티브 INSERT 쿼리에 남아있던 Oracle 전용 `SYSDATE`가 MySQL엔 없는 함수라 표준 SQL `CURRENT_TIMESTAMP`로 바꿨다(`4c42****`).

**테이블명 대소문자** — `@Table(name = "JIPDAUM_CATEGORY")`처럼 명시했는데도 `Table 'jibdaum.jipdaum_category' doesn't exist` 에러가 났다. 원인은 Spring Boot 기본 네이밍 전략이 명시한 이름까지 강제로 소문자로 바꿔버리는 것 — Oracle은 식별자를 대문자로 정규화해 비교하는 경우가 많아 이 변환이 드러나지 않았지만, MySQL은 파일시스템 기반으로 대소문자를 구분해 Django가 만든 실제 테이블명과 어긋났다. 물리 네이밍 전략을 표준 전략으로 고정해 지정한 이름을 그대로 쓰도록 해결했다(`80f6****`).

**자동 증가 컬럼** — Oracle의 시퀀스 기반 방식 대신 MySQL 네이티브 `AUTO_INCREMENT`를 그대로 쓸 수 있어, `@GeneratedValue(strategy = IDENTITY)` 하나로 끝났다.

## 트레이드오프 — 감수한 대가는 실제로 드러났다

"스키마는 Django가 소유한다"는 원칙은 반대로 말하면, **Spring 코드가 스키마에 없는 걸 기대하는 순간 즉시 깨진다**는 뜻이다. 실제로 Spring 엔티티에 `collection` 필드가 pull로 새로 들어왔는데, 그 필드에 해당하는 Django 마이그레이션이 로컬 DB에 미적용 상태라 `Unknown column 'p1_0.collection'`으로 테스트가 실패한 적이 있다. Django 쪽에서 마이그레이션을 실행하자 바로 해결됐지만, 이건 코드 리뷰만으로는 못 잡는 유형의 실패다 — 두 저장소의 변경 순서가 어긋나면 항상 재현 가능하다.

이 트레이드오프는 되돌릴 수 있는 게 아니라 이 아키텍처를 선택한 이상 계속 안고 가야 하는 비용으로 판단했다. 대신 "Spring 배포 전 Django 마이그레이션이 먼저 적용됐는지 확인한다"는 걸 배포 체크리스트에 넣는 방향으로 완화하는 게 다음 개선 과제로 남아있다.

## 결론

이 작업의 본질은 "Oracle 문법을 MySQL 문법으로 바꾼 것"이 아니라 **"두 프레임워크 중 하나에 스키마 소유권을 전담시키고, 그 대가로 소유하지 않은 쪽이 감수해야 하는 실패 모드를 받아들인 것"**이다. Oracle→MySQL 이관에서 만난 기술적 차이(SYSDATE, 네이밍 전략, 드라이버)는 하루 만에 해결된 국지적 이슈였던 반면, 스키마 소유권 분리라는 아키텍처 결정은 지금까지도 유효한 제약으로 남아 있고, 실제로 그 트레이드오프가 테스트 실패로 한 번 드러난 사례가 이 문서의 핵심이다.
