이 문서가 다루는 범위: 이 저장소(Team-DaumAna, 프론트엔드 + Django)에서 발생한 오류 중
영향 범위가 크거나(전체 크래시, 배포 불능, 인증 전면 차단) 근본 원인 진단에 여러 단계가

> 참고: 이 저장소의 실제 커밋은 2026-07-13(초기 커밋)부터 시작한다. 6월 작업 이력은

## 1. PASS 인증 도입이 촉발한 프로덕션 회원가입/로그인 전면 차단 + 배포 파이프라인 정지 복합 장애

**기간**: 2026-08-23 (`1b14acc` → `94eaad4` → `79f1975`)
**심각도**: 최상 — 신규 가입/로그인이 프로덕션에서 전부 실패, 게다가 원인 파악 도중
배포 자체가 멈춰 있어 수정 커밋이 반영조차 안 되는 이중 장애였다.

### 증상
hCaptcha 위젯을 실제 통신사 PASS 인증 흐름처럼 보이게 하는 데모(`PassVerifyModal`)로
교체(`1b14acc`)한 뒤, 운영 도메인(jipdaum.life)에서 회원가입·로그인·소셜로그인이
전부 실패했다.

### 원인 진단 과정
1. `PassVerifyModal`은 실제 검증 없이 `mock-pass-...` 형태의 더미 토큰만 만들어
   백엔드로 보내는 화면 흐름 재현용 컴포넌트였다.
2. 반대로 Spring 백엔드(`HCaptchaService.verify()`)는 그 값을 진짜 hCaptcha
   siteverify API로 검증하려 시도 — 당연히 hCaptcha 서버가 그 mock 토큰을 전부
   거부해 가입/로그인/소셜로그인 3개 지점이 모두 막혔다.
3. 프론트만 되돌리면(`94eaad4`) 끝날 문제였는데, 되돌린 커밋을 배포해도 운영 화면에
   `hCaptcha has failed to initialize` / 콘솔 `Missing sitekey` 에러가 계속 남았다.
4. `VITE_HCAPTCHA_SITE_KEY`가 애초에 PASS 전환 커밋에서 `.env.example`과 함께
   지워지며 Cloudflare Pages 프로젝트 환경변수에서도 빠져 있었던 것을 확인, 등록.
5. 그런데도 동일 에러가 지속 — Vite 환경변수는 **빌드 시점에 번들에 굳어지므로**
   변수만 새로 등록해도 재빌드 전에는 반영되지 않는다는 걸 재확인.
6. GitHub Checks API로 커밋별 Cloudflare Pages 빌드 상태를 직접 조회해보니, `main`이
   새 커밋(`94eaad4` 등)을 여러 개 쌓았는데도 Cloudflare Pages가 계속 예전 커밋
   (`4ddaeab`)에 멈춰 새 빌드를 아예 시도하지 않고 있었다.
7. 같은 커밋(Cloudflare Pages 이관)에서 `vite` 7로 업그레이드된 상태였는데, vite 7의
   `engines.node` 요구사항(`^20.19.0 || >=22.12.0`)을 Cloudflare Pages의 기본 빌드
   Node 버전(18.x대)이 못 맞춰 빌드가 계속 조용히 실패(또는 스킵)하고 있었다고 판단.

### 근본 원인
두 가지가 같은 시점에 겹친 복합 장애였다:
- **애플리케이션 레벨**: 프론트(mock 토큰 생성)와 백엔드(실제 hCaptcha 검증)가
  서로 다른 신뢰 모델로 배포되어 계약이 깨짐.
- **인프라 레벨**: 프레임워크(vite 7) 요구 Node 버전과 배포 플랫폼(Cloudflare Pages)
  기본 Node 버전의 불일치로, 정작 고친 코드가 배포 파이프라인에 아예 올라가지 못함.

### 해결
- `PassVerifyModal.jsx/.css` 삭제, `Login.jsx`/`Register.jsx`/`ChatBot.jsx`
  (SignupPanel)/`AuthModalContext.jsx`를 원래의 `<HCaptcha />` 위젯으로 복원.
- 별도 저장소 `jipdaum-spring`의 `HCaptchaService.verify()` 호출 지점도 함께 원복.
- `VITE_HCAPTCHA_SITE_KEY`를 `.env.example`에 복원 + Cloudflare Pages 프로젝트
  환경변수에 재등록.
- `frontend/.nvmrc`(20) 추가 + `package.json`에 `engines.node: ">=20.19.0"` 명시해
  Cloudflare Pages가 올바른 Node 버전으로 빌드하도록 강제(`79f1975`).

### 재발 방지
- 인증처럼 프론트/백엔드가 토큰 포맷을 공유하는 기능은 두 저장소를 **같은 커밋
  타이밍에** 되돌릴 수 있어야 한다 — 한쪽만 롤백하면 계약이 다시 깨진다.
- 빌드 도구(vite 등)의 메이저 업그레이드는 배포 플랫폼의 런타임 버전 고정
  (`.nvmrc`/`engines`)과 항상 세트로 커밋한다.
- "코드를 고쳤는데도 운영에 안 보인다"는 신호가 오면 코드 문제로만 보지 말고
  배포 파이프라인이 새 커밋을 실제로 물어가고 있는지(CI/CD 상태)부터 확인한다.

## 2. 상품 이미지 원본 용량 폭증(107MB) → 배포된 메인 페이지가 완전히 빈 화면

**기간**: 2026-08-24 (`2b6d959`)
**심각도**: 높음 — 사용자 리포트가 "배포된 화면이 아무것도 안 보이는데?"였을 만큼
메인 페이지 전체가 렌더링되지 않는 것처럼 보였다.

### 증상
메인 상품 14종을 새 사진으로 전면 교체한 뒤 배포하자, 로컬에서는 멀쩡했던 화면이
운영 배포본에서는 아무것도 뜨지 않았다.

### 원인 진단 과정
새로 받은 상품 사진 14장이 원본 PNG 그대로(장당 5~13MB) 커밋되어 있었고, 합계
107MB에 달했다. 로컬 개발 서버(파일시스템 직접 서빙, 캐시 워밍된 상태)에서는
체감 지연이 적었지만, 실제 네트워크를 통해 받아야 하는 배포 환경에서는 브라우저가
초기 페인트에 필요한 리소스를 사실상 못 받아와 "빈 화면"으로 보였다.

### 근본 원인
이미지 최적화(리사이즈/포맷 변환) 단계 없이 디자인 원본 파일을 그대로 정적 자산
파이프라인에 커밋한 것. 로컬 환경은 네트워크 지연을 감추기 때문에 로컬 QA만으로는
드러나지 않는 유형의 버그였다.

### 해결
`sharp`로 표시 크기(1600px 이내)로 리사이즈 + JPEG 재인코딩(quality 82) 처리해
합계 107MB → 1.5MB로 축소. 이후 추가된 인테리어 컷 이미지도 같은 파이프라인을
거쳐 커밋하도록 절차화(`df4e226`에서 5:6 비율 1000×1200 통일 크롭까지 이어짐).

### 재발 방지
- 상품/에셋 이미지는 커밋 전 리사이즈+재인코딩을 거치는 것을 기본 절차로 굳힘.
- 로컬 QA만으로 "화면이 안 뜨는" 유형의 버그를 잡을 수 없다는 걸 재확인 —
  이후 배포 확인은 Cloudflare Pages/GitHub Checks API로 실제 빌드·서빙 상태를
  직접 조회하는 흐름으로 굳어졌다(`CLAUDE.md` 배포 섹션).

## 3. `res.data`가 배열이 아닐 수 있다는 걸 검증 안 해 홈페이지 전체가 하얗게 크래시

**기간**: 2026-08-25 (`7823b61`)
**심각도**: 높음 — 특정 기능 하나가 아니라 **홈페이지 전체**가 렌더링 도중 죽는
React 크래시였다.

### 증상
"로그인 모달이 느리게 뜬다"는 요청으로 hCaptcha CDN을 preconnect로 예열하는 작업을
하던 중, 실제로는 로그인 모달 문제가 아니라 홈페이지 자체가
`photoReviews.map is not a function`으로 완전히 크래시하고 있는 것을 발견했다.

### 원인 진단 과정
포토리뷰 목록 API(`getPhotoReviews`) 호출 응답을 검증 없이 그대로
`setPhotoReviews(res.data)`로 state에 넣고, 렌더링에서 바로 `.map()`을 호출하고
있었다. 백엔드가 예상과 다른 응답(로그인 필요 안내 HTML, 에러 객체 등 배열이 아닌
값)을 준 순간 `.map is not a function`으로 컴포넌트 트리 전체가 터졌다.
이전(8/15)에도 같은 계열의 버그(비로그인 상태 상품 상세 빈 화면, `b0acbeb`)를 고친
적이 있어, 같은 패턴이 또 있는지 전수 점검했다.

### 근본 원인
"API는 항상 배열을 준다"는 암묵적 가정 위에 state를 설계하고, 그 가정이 깨지는
경로(오프라인, 인증 만료, 백엔드 에러 응답 등)에 대한 방어 코드가 없었던 것.
같은 패턴이 `SearchResults`, `Checkout`/`CheckoutKoreanHall`(쿠폰 목록),
`TrackingModal`(배송조회)까지 총 5곳에서 발견됐다 — 한 번의 부주의가 아니라
반복된 설계 습관이었다는 뜻.

### 해결
5곳 모두에 `Array.isArray(res.data) ? res.data : []` 형태의 가드를 추가해,
백엔드가 예상과 다른 응답을 줘도 해당 화면만 빈 상태로 넘어가고 페이지 전체가
죽지 않도록 격리했다.

### 재발 방지
- API 응답을 state에 넣기 전 타입 가드를 통과시키는 걸 팀 컨벤션으로 굳힘
  (이후 커밋들, 예: `Sidebar.jsx`의 `fetchCartCount`도 동일 패턴 준수 — `7acef82`).
- 크래시 재현을 계기로 "다른 곳에도 같은 버그가 더 있는가"를 항상 같이 확인하는
  습관 — 이 사례처럼 최초 증상(모달 지연)과 실제 버그(전체 크래시)가 다를 수 있다.

## 4. Django `AUTH_USER_MODEL` 오류로 셸/마이그레이션이 완전히 막힘

**기간**: 초기 Django 백엔드 구축 단계 (2026-07 초, 저장소 커밋 `44640db` 이전 로컬 작업)
**심각도**: 중간 — 배포 영향은 없었지만(아직 배포 전), 백엔드 로컬 개발이 완전히
멈추는 블로커였다.

### 증상
`python manage.py shell` 실행 시
`LookupError: App 'Jipdaum' doesn't have a 'User' model` 에러로 셸 자체가 죽었다.

### 원인 진단 과정
`settings.py`의 `AUTH_USER_MODEL`이 `'Jipdaum.User'`로 설정돼 있었는데, 실제
`User` 모델은 이미 리팩터링을 거쳐 `Users` 앱으로 분리된 상태였다. Django는
`AUTH_USER_MODEL`에 지정된 `앱이름.모델명` 문자열을 앱 레지스트리에서 그대로
찾기 때문에, 앱 분리 시점에 이 설정을 같이 안 바꾸면 임포트가 아니라 런타임
레지스트리 조회 단계에서 실패한다.

### 근본 원인
모델을 다른 앱으로 이동하는 리팩터링을 하면서, 문자열로 참조되어 있어 IDE의
"참조 찾기"에 걸리지 않는 설정 값(`AUTH_USER_MODEL`)을 같이 갱신하지 않은 것.

### 해결
`AUTH_USER_MODEL = 'Users.User'`로 수정.

### 재발 방지
- Django에서 `앱.모델` 형태의 문자열로 참조되는 설정(`AUTH_USER_MODEL`,
  `ForeignKey("app.Model")` 등)은 모델을 다른 앱으로 옮길 때 같이 검색해서
  갱신하는 걸 체크리스트에 넣는다 — 정적 분석/IDE 리팩터링 도구가 못 잡는 지점.

## 5. `ScrollToTop` 파일명 대소문자 불일치 — 로컬(Windows)은 정상, CI(Linux)만 빌드 실패

**기간**: 2026-08-20 (`694f3bd`)
**심각도**: 중간 — 기능 자체엔 문제가 없었지만, 배포 파이프라인이 계속 실패해
머지된 코드가 운영에 반영되지 않는 상태였다.

### 증상
GitHub Actions(Linux 러너)에서 프론트 빌드가
`Could not resolve "./component/ScrollToTop"` 류의 에러로 계속 실패했다. 로컬
(Windows)에서는 동일 코드가 아무 문제 없이 빌드/실행됐다.

### 원인 진단 과정
실제 파일명과 `import` 경로의 대소문자가 서로 달랐다(예: `scrollToTop.jsx` vs
`import ScrollToTop from "./component/ScrollToTop"`). Windows(NTFS 기본 설정)와
macOS(APFS 기본 설정)의 파일시스템은 대소문자를 구분하지 않아 실제로는 다른
경로인데도 로컬에서는 그냥 매칭돼 열렸던 것. 반면 GitHub Actions 러너(Ubuntu,
ext4)는 대소문자를 엄격히 구분해 그 경로가 존재하지 않는 것으로 처리했다.

### 근본 원인
개발 환경(Windows/Mac)의 대소문자 비구분 파일시스템이 대소문자 불일치를
가려주고 있었을 뿐, 애초에 파일명과 import 경로가 어긋나 있던 잠재 버그.

### 해결
실제 파일명을 import 경로와 동일한 PascalCase(`ScrollToTop`)로 통일.

### 재발 방지
- 이런 유형의 버그는 로컬에서 아무리 테스트해도 재현되지 않는다 — CI가 Linux
  러너를 쓰는 이상 "로컬에서 됐다"는 검증이 되지 않는다는 걸 팀 규칙으로 인지.
  (근본적으로는 `git config core.ignorecase false`나 파일명 린트로 사전 차단하는
  방법도 있으나, 이 프로젝트 규모에서는 재발 시 즉시 대소문자 통일로 대응하는
  현재 방식을 유지하기로 함 — 재발 빈도가 낮아 별도 도구 도입은 보류.)

## 6. 브라우저 창 리사이즈 시 가로 스크롤 패널이 서로 겹쳐 보이는 문제

**기간**: 2026-08-30
**심각도**: 낮음~중간 — 크래시나 배포 실패는 아니지만, 메인 페이지의 핵심 연출
(가로 스크롤 패널)이 창 크기를 바꿀 때마다 깨져 보이는 눈에 띄는 시각적 버그였다.

### 증상
브라우저 창을 최소화했다가 다시 최대화(또는 창 크기를 임의로 조절)하면, 특정
패널이 화면 영역에 딱 맞게 나오지 않고 옆 패널의 일부와 겹쳐서 함께 보였다.

### 원인 진단 과정
1. 홈의 각 섹션은 `w-screen`(=`100vw`) 폭의 패널을 가로로 나열하고, `lenis`+
   `lenis/snap`(가로 스크롤 + 패널 스냅)으로 넘긴다.
2. `Snap` 라이브러리 소스(`node_modules/lenis/dist/lenis-snap.mjs`)를 직접 열어
   확인해보니, `window resize` 이벤트가 오면 `Snap.onWindowResize`가 `viewport`
   치수만 갱신할 뿐, 현재 보고 있던 패널로 다시 스냅해주는 로직이 없었다.
3. 각 패널의 "문서 기준 왼쪽 좌표"(`SnapElement.rect.left`)는 스크롤할 때마다
   재계산되는 게 아니라, `document.body`의 `ResizeObserver`가 잡히는 시점에
   **500ms 디바운스**로만 갱신된다는 것도 확인했다.
4. 처음에 "리사이즈 후 200ms 뒤 현재 패널로 재스냅"하는 핸들러를 추가했더니
   증상이 그대로 재현됐다 — Snap 내부의 500ms 디바운스보다 먼저 실행되어,
   아직 갱신 안 된(리사이즈 전) 좌표 기준으로 스냅해버렸기 때문이었다.

### 근본 원인
패널 폭이 `vw` 기반이라 창 크기가 바뀌면 패널 폭 자체가 바뀌는데, Lenis가
기억하는 스크롤 위치(px)는 리사이즈 전 값 그대로 남는다. 예를 들어 "2번째 패널
시작 = 1920px"였다가 창을 줄이면 실제 2번째 패널 시작은 1280px로 바뀌는데,
스크롤은 여전히 1920px에 멈춰있어 두 패널이 반씩 걸쳐 보이는 것.

### 해결
`App.jsx`의 Lenis/Snap 초기화 지점에 `window resize` 리스너를 추가해,
리사이즈가 끝나면(디바운스) `lenis.resize()`로 스크롤 한계를 다시 계산하고
`snap.goTo(snap.currentSnapIndex)`로 현재 패널로 재정렬한다. 디바운스 지연은
Snap 내부 좌표 갱신(500ms)보다 반드시 늦게 실행되도록 600ms로 설정했다.

### 재발 방지
- 서드파티 라이브러리가 "리사이즈에 대응한다"고 해서 그게 "현재 상태를
  일관되게 유지한다"는 뜻은 아니다 — 이번처럼 치수만 갱신하고 위치 보정은
  안 해주는 경우가 있으니, 라이브러리 소스를 직접 열어 어떤 것까지 자동으로
  처리하는지 확인한 뒤 나머지를 채워 넣어야 한다.
- 여러 개의 디바운스/타이머가 같은 이벤트에 반응해 서로 다른 지연으로 동작할
  때는 실행 순서를 반드시 명시적으로 보장해야 한다(여기서는 상수 지연 비교로
  단순 처리했지만, 근본적으로는 라이브러리의 내부 갱신 완료를 이벤트로 받을 수
  있으면 더 견고하다).
